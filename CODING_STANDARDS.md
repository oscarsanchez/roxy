# Coding Standards

The judgement calls a reviewer checks. Mechanical rules (tests, shell syntax, Compose config, glossary terms, test imports, paths into `out/`) are enforced by `scripts/check`; read it there.

## Trust

- **Trust decisions read lab-owned state.** A guard, the Target Device decision or a rewrite decides from what the lab itself established: the listener a request arrived on, and `flow.metadata` set by an earlier addon (`proxy_base`, `lab_refusal`). A header the client or the Origin sets is data, not evidence. The one exception is a header whose sender the lab has proven: tunnel headers such as `CF-Connecting-IP`, trusted only on the tunnel listener, which only cloudflared reaches (`proxy/lab/clients.py`).
- **Runtime-specific trust lives in that runtime's config.** Shared config (`proxy/config/*.json`, addon option defaults) applies to every runtime: native, Compose and CA Routing alike. Trust that one runtime needs, such as Docker Desktop's `192.168.65.1`, goes in that runtime's own config (`LAB_LAN_SUBNETS` in `compose.yaml`), so no other runtime inherits it.
- **The secret check comes first on the tunnel.** An unauthenticated tunnel request learns nothing about the lab: it gets 403 `secret-segment` whatever it sends, with no refusal reason, header or behaviour that reveals another guard, the routing or the config.
- **The lab secret never reaches printed output.** Anything a command prints that can hold the secret (a public Proxy Base, a URL, a banner or cell line) goes through `redact_secret` (`scripts/lib.sh`), which shows it as `<secret>`. Only `roxy status --show-secret` prints the secret itself.

## Boundaries

- **External tools consume the lab's outputs.** `grid/` and any other tool read what the lab publishes through the `roxy` CLI (the flows as `roxy flows --json` sums them up, with each flow's Target Device name and refusal reason; the lab's state from `roxy status --json`), never mitmweb's API or a flow's comment, and leave the lab's rules in `proxy/lab/`. A rule change in the lab needs no matching edit elsewhere.
- **Routine commands never fetch every flow's body.** What runs on every call (`roxy status`, `roxy launch`, the grid's lab-state check) never fetches every flow: mitmweb's full `flows/dump` carries every body of a long session. When it reads flows, it narrows them with a mitmweb filter (`roxy status` asks for `~marked`, the flows a Scenario rule acted on). The full `flows/dump` stays behind `roxy flows` (`roxy export` reads the Recording file, never mitmweb).
- **One Prefixed URL builder and parser per codebase.** The proxy builds and parses through `proxy/lab/prefixed_url.py`; each Lab App flavour builds through its own (`PrefixedUrl.brs`, `prefixed-url.ts`), and each kit flavour through its own (`RoxyUrl` in `RoxyKit.brs`, `prefixedUrl` in `roxy-kit.ts`). The rule binds code that builds or parses requests: a second regex or an inline concatenation there is a finding. A test's expected URL, written out as a literal, is not a builder.
- **A Run is billed until stopped.** Code that starts a Cloud Device Run starts it inside the `try` whose `finally` stops it. On Ctrl-C or a kill it waits for `rce` to exit, then confirms with `rce device status` that the Run ended. A Run it didn't start is someone else's: use it and leave it running. Reference: `cloud_run` in `grid/run_cell.py`; the rce CLI's skill, Money and permanence.
- **Personal settings live in the settings root.** Secrets, device names and addresses, and LAN subnets are read from the settings root (`scripts/lib.sh`, `proxy/lab/config.py`), never from the repo. The repo ships `settings.example/` with documentation IPs (192.0.2.0/24, 198.51.100.0/24, 203.0.113.0/24) and made-up names, and tests run against a temp settings root seeded from it; `install.sh` seeds none of its made-up values into a user's settings root.

## Tests

- **Tests write only to temp roots.** A test points all three roots the scripts write to at temp folders: the settings root (`ROXY_CONFIG_DIR`), the user data directory (`XDG_DATA_HOME`) and the build output and logs (`ROXY_OUT_DIR`, the checkout's `out/` by default), as `scripts/check` does. A script that writes one of them goes through its variable in `scripts/lib.sh`, never a path of its own. A test that runs `roxy start` (`scripts/start-lab`) moves the lab's ports to free ones too (`scripts/tests/lab-ports.sh`): the start checks its ports, and a test must never see a lab the user is running.

- **Fixtures from real material are rewritten whole.** A test fixture or doc example derived from a Product App's traffic, rules or config replaces every identifying part, not just the hostname: paths, tokens, IDs, query values and file names become made-up ones on documentation hosts (example.com/.net/.org). The leak check only knows the terms on its list; a client-specific path shape passes it.

- **Proxy tests run at Seam A, through the full chain.** A test builds a flow, runs it through `tests/chain.py`, and asserts on what reaches the Origin or the client, or what the lab shows (the mitmweb comment and mark, the flows summary), so addons can be split or merged with every test still green. The exceptions are modules the CLI uses too, tested at their own interface: App Profiles (`proxy/lab/app_profiles.py`), whose tests call `AppProfiles` against a temp settings root and temp git repos, the Settings Root (`proxy/lab/settings_root.py`), whose tests call `SettingsRoot` against a temp settings root with its ports (ECP, `rce`, this Mac's address, the random source, the SSDP search, the tools on the PATH) faked, and the Lab Session client (`proxy/lab/lab_session.py`), whose tests drive `LabSession` against mitmweb's API in memory. The harness stands in for the one mitmproxy internal the lab reaches into, the client connection's writer (`client_writer` in `proxy/lab/throttle.py`); `tests/test_mitmproxy_contract.py` checks that path against a real mitmdump, from the client's side only.
